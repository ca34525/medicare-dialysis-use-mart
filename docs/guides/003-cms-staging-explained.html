The main idea: unpack a sealed shipment

The sealed shipment

Plan 002 stored the exact CMS bytes as an immutable, content-addressed blob. Its manifest acts like a receiving record: it says which file arrived, how large it was, which columns it had, and which cryptographic hash identifies it.

Plan 003 checks that receiving record again before it opens anything. The raw blob and manifest remain unchanged.

The labeled workbench

DuckDB receives only required columns as raw text. dbt then selects the intended county rows, types metrics, assigns explicit missingness statuses, checks the declared grain, and attaches source lineage to every result.

The result is easier to query, but it can still be traced to the sealed shipment.

County-stage grain: one five-character county FIPS × one CMS calendar year

Denominator and meaning: metrics remain on their CMS-defined scales and Original Medicare denominators. Observed outpatient dialysis use among Original Medicare beneficiaries is not relabeled as kidney disease prevalence, unmet need, disease burden, or an intervention opportunity.

What happens from input to output

  1. 1

    Verify

    Read canonical manifest JSON and recheck the blob path, SHA-256, bytes, rows, schema hash, header hash, and raw contract.

  2. 2

    Load strings

    Copy required CSV values into a run-scoped DuckDB table as text. Leading zeros and missingness tokens remain visible.

  3. 3

    Type and scope

    dbt keeps exact County + All rows, excludes documented pseudo-geographies, and creates fixed-point values plus statuses.

  4. 4

    Block or pass

    Unit, contract, data, and reconciliation tests must pass. Invalid FIPS, invalid numbers, or duplicate county-years stop the build.

Input lineage

Manifest run ID, content SHA-256, retrieval timestamp, source modified date, and source year.

Output structure

Raw string, typed value, and interpretation status for each governed numeric metric.

Safe rerun

An identical load is a no-op. A different manifest cannot overwrite a DuckDB file that already represents other lineage.

Why one metric becomes three columns

A typed value alone cannot explain why it is missing. For example, benes_op_dlys_pct_raw, benes_op_dlys_pct, and benes_op_dlys_pct_status travel together.

The county gate is narrow and auditable

Rows that enter

  • BENE_GEO_LVL = County
  • BENE_AGE_LVL = All
  • Five ASCII digits in BENE_GEO_CD
  • One exact exception: State DC, code 11, All becomes county-equivalent 11001

Rows that do not enter

  • Age subgroups, state rows, and national rows
  • Anchored source UNKNOWN pseudo-counties
  • Territory FIPS prefixes outside the MVP
  • Malformed or duplicate county-year keys
No fuzzy geography: the transformation does not use ZIP codes or name similarity. The DC rule is an exact, audited source-shape exception; a simultaneous County 11001 row blocks as ambiguous.

Checks are part of the transformation

The committed fixture is synthetic and network-free. It contains a leading-zero county, District of Columbia, suppression, blank, NA, zero, whitespace, state/national/age rows, an UNKNOWN row, and a territory row. Separate failure injections add malformed FIPS, invalid numeric text, and a duplicate county-year.

Python loader tests

Prove manifest support, canonical JSON, path containment, reconciliation, text preservation, lineage, atomic output, idempotency, and conflict blocking.

dbt unit and data tests

Prove County + All selection, missingness, model contracts, lineage, county FIPS, unique grain, numeric validity, and row reconciliation.

Fixture integration

Loads DuckDB, runs dbt build, inspects every required metric, and proves a repeat build has the same ordered semantic checksum.

What does “blocking” mean here?

A failed integrity check creates no final DuckDB file. A dbt quality failure returns a failed build and cannot update any published mart or latest-successful pointer—neither exists in this stage. Raw evidence is never rewritten.

Does the fixture prove current national row counts?

No. The fixture proves transformation rules deterministically. Live-source counts are separate, dated evidence and are not fetched by the default test path.

What remains outside this plan

  • The SVI-specific -999 rule and paginated SVI ingestion.
  • State and national benchmark facts were outside Plan 003 and are now built separately by Plan 006; they never mix into county staging.
  • Dimensions, final facts, and CMS-to-SVI reconciliation were outside Plan 003 and are now completed by Plans 005-006. Percentiles and screening quadrants remain deferred.
  • Facility geography and context, publication, Airflow, Power BI, hosting, and cloud work.
  • Patient-level data, clinical inference, causal claims, opaque scores, automated decisions, or final site-selection recommendations.

Plans 004-006 subsequently completed the SVI path, governed CMS facts, and pinned geography reconciliation. Screening classification still waits for its own transparent plan.

Short glossary

Blob
The exact immutable source bytes, named by their content hash.
Manifest
A canonical JSON record identifying a snapshot and its validation evidence.
DuckDB
A local analytical database holding run-scoped raw strings and staging output.
dbt
A tool that builds documented SQL models and runs unit, contract, and data tests.
Grain
What one row represents: one county FIPS in one CMS year here.
FIPS
A five-character county identifier stored as text because leading zeros matter.
Lineage
Fields tracing an output row to its manifest, blob, retrieval, and source vintage.
Semantic checksum
A hash of ordered query results, comparing meaning rather than physical database bytes.
