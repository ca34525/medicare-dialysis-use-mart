What is an ingestion manifest?

The extractor receives a changing CMS file, proves that the delivery is complete and acceptable, stores the exact file once, and writes a small receipt describing exactly what happened. That receipt is the manifest.

Start with an analogy

A warehouse receiving desk

The project does not unpack a shipment onto production shelves merely because a truck arrived.

CMS shipment a changing CSV download
→
Receiving desk count, inspect, fingerprint, record
“Did we receive the right shipment, in full, without changing it—and can we prove that later?”

The extractor starts with the durable CMS catalog, resolves the current official file, and downloads it into a temporary area. It checks the delivery before anything becomes a permanent raw snapshot.

The exact shipment becomes the blob. The receiving record becomes the manifest. Later transformations use those local, verified artifacts instead of contacting CMS again.

Three objects

Temporary file, blob, manifest

These names describe three different responsibilities. Keeping them separate is what makes failure safe and history reproducible.

1 Untrusted delivery

Temporary file

The download lands under data/raw/.tmp/<run-id>/. It may be incomplete or invalid, so no downstream model should use it yet.

2 Exact stored content

Blob

“Blob” means a stored object treated as bytes. Here it is still a CSV, but its filename is the SHA-256 fingerprint of its exact contents. Identical contents share one blob.

3 The receipt

Manifest

A small canonical JSON document records the source, run, timestamps, counts, hashes, schema evidence, and blob path. It tells a later build which verified bytes to use.

Why all the emphasis on bytes?

Bytes are the raw file’s exact identity

A CSV is text to a person, but it is a sequence of bytes to a computer. That lower-level view lets the project prove sameness without interpreting the data first.

Two tables can look equivalent on screen yet have different raw bytes. Re-saving can change line endings, quoting, column order, encoding, or a leading zero.

  • Byte count helps detect a cut-off transfer.
  • SHA-256 turns all bytes into a stable 64-character fingerprint.
  • Unchanged bytes preserve *, blank, NA, and numeric 0 as distinct raw evidence.
  • Binary streaming avoids loading the roughly 58 MB source into memory or silently reserializing it.

Safe publication

Permanent means validated

The pipeline uses temporary paths on the same filesystem and no-overwrite publication. A partially downloaded file can never masquerade as a successful snapshot.

Step 1

Stage

Create a new run-scoped temporary file.

Step 2

Validate

Re-read the CSV and reconcile bytes, rows, schema, and grain.

Step 3

Link blob

Create the hash-named final blob without overwriting one that exists.

Step 4

Write receipt

Publish canonical manifest bytes only after the blob is proven valid.

If any check fails:

The temporary partial file is cleaned up. No final manifest appears, no existing blob is changed, and previously published mart state remains intact.

Retry with judgment

Try transport again; never argue with evidence

A timeout may clear on the next attempt. A missing required column will not. Retries are bounded and reserved for plausibly temporary delivery problems.

Which failures the extractor retries
Action Failure examples Reason
Retry Connection failure, timeout, HTTP 408, HTTP 429, HTTP 5xx, incomplete body versus Content-Length The source or network may recover. Each partial file is removed first, delays back off, and attempts are capped.
Stop Wrong dataset, duplicate header, missing required field, incompatible type, malformed or duplicate grain, failed row/hash reconciliation The received evidence is unacceptable. Repeating the same interpretation would hide a contract or data-quality problem.

What the live check taught us

A strict gate found a real source detail

The live full-file run was not just ceremonial. It exercised an invariant against all 36,994 source rows and exposed a grain detail that the small sample could not prove.

!

BENE_GEO_DESC belongs in the raw transport grain

CMS uses the same blank State code for two distinct pseudo-rows named Territory and ZZ. A grain made only from year, level, code, and age would falsely call them duplicates.

The fix added the required description field to the raw grain. It did not weaken duplicate detection, and it did not change the later county fact grain. This is the value of blocking publication on unexplained duplicates.

A clear boundary

What Plan 002 does—and does not do

Raw ingestion protects evidence. Meaningful metrics and county modeling belong to later transformations that consume the immutable snapshot.

Completed here

  • Resolve the current file from durable official CMS metadata.
  • Download with timeouts and bounded transient retries.
  • Preserve, count, and hash the exact response bytes.
  • Validate headers, types, rows, and every complete raw grain.
  • Publish immutable content-addressed blobs and run manifests.
  • Make repeated content and repeated runs deterministic and safe.

Intentionally left for later

  • Convert *, blank, or NA into typed nulls and statuses.
  • Normalize county FIPS or filter County + All rows.
  • Exclude territories or UNKNOWN pseudo-counties from the MVP mart.
  • Build DuckDB, dbt, Parquet, Airflow, or Power BI assets.
  • Calculate observed outpatient dialysis use among Original Medicare beneficiaries.
  • Update a latest-successful pointer before every later publication gate passes.

Small glossary

Terms you will see again

Open any term for a plain-language explanation.

Byte

A single unit of stored digital information. A file is an ordered sequence of bytes. At the raw boundary, preserving that exact sequence prevents accidental cleanup or reinterpretation.

Blob

Short for “binary large object.” In this project it means one immutable stored CSV treated as exact bytes. Text files can be blobs; “binary” describes how storage treats the object, not whether a person can read it.

Hash and SHA-256

A hash function turns any amount of input into a fixed-size fingerprint. SHA-256 produces 256 bits, usually written as 64 hexadecimal characters. Matching hashes are strong evidence of matching bytes; a different hash means the content changed.

Content-addressed storage

A layout where a file’s address comes from its content hash rather than a friendly mutable name such as “latest.csv.” The same bytes naturally point to the same path.

Manifest

A small machine-readable receipt that describes a larger artifact: where it came from, when and how it was retrieved, its counts and hashes, its schema evidence, and where the exact blob is stored.

Lineage

The trace from an output back through its run, manifest, immutable raw bytes, resolved source version, stable official dataset, and extraction code.

Canonical JSON

JSON serialized by one exact rule—sorted keys, compact separators, UTF-8, stable list ordering, and a final newline here—so the same manifest data always produces the same bytes.

Atomic publication

A publication step that appears complete all at once. Other work never sees a half-written final file. This extractor stages and validates first, then creates final immutable files on the same filesystem.

Idempotent and no-op

An idempotent operation can be repeated without creating duplicates or changing the correct final state. A no-op is a successful repetition that records or returns the existing result without republishing identical content.

Reconciliation

Independently checking that related facts agree—for example, downloaded byte count versus HTTP metadata, CSV rows versus CMS metadata, and a manifest hash versus the stored blob.

Content-Length

An optional HTTP response header that says how many bytes the server intends to send. If the extractor receives a different count, it treats the transfer as incomplete.

ETag and Last-Modified

Optional HTTP headers that provide additional source-version clues. They are retained when CMS sends them, but the extractor still computes its own byte count and cryptographic hashes.

The takeaway

The manifest turns a download into reproducible evidence.

The blob preserves exactly what CMS sent. The manifest proves which blob a run used and why it was accepted. Together they let later transformations proceed from stable local evidence even after the live CMS file changes.
